# Android Compose stage experiment

This developer-only experiment checks the next layout-migration boundary before the real Android game screen
changes. `ComposeStageProbeActivity` exists in the debug source set and debug manifest only. There is no launcher
entry, player preference or alternate release screen.

Both modes reuse `EmulatorEngine`, `EmulatorView`, `GbaInput`, `TouchControlsView` and its `TouchInputWindows`, plus
the existing shared companion UI. They run an original diagnostic generated by `linux/make_diagnostic.py`.
Game data stays under `cache/compose-stage-probe`; the native panel mode has its own preference namespace.
The probe mutes game sound without changing the player's stored sound preference.

- `layout=native` uses the existing `GameStageLayout`, `SidePanel` and `PortraitPanel` inside a native view slot.
- `layout=compose` puts the same renderer and native controls adapter in the existing shared `GameScreen` slots.
- Both modes use the same debug toolbar and shared companion window overlay.

The native baseline is inside the same Compose debug host. It provides a controlled comparison of the inner layout
owners, not an exact benchmark of the production activity. The native portrait grip and shared docked layout also
have different available sizes; this experiment does not establish complete layout parity.

## Run

Build a debug APK and install it on an ARM64 Android emulator or device:

```sh
./gradlew :app:assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

From the repository root, generate the original diagnostic and copy it into the debug app's cache.
No commercial game is needed. Do not commit the generated ROM or save. If more than one Android device is connected,
use `adb -s <serial>` for each command.

```sh
probe_source="$PWD/linux/make_diagnostic.py"
probe_dir="$(mktemp -d)"
(cd "$probe_dir" && python3 "$probe_source")
adb push "$probe_dir/diagnostic.gba" /data/local/tmp/pokedaisy-stage-diagnostic.gba
adb shell run-as com.pokedaisy.app mkdir -p cache/compose-stage-probe
adb shell run-as com.pokedaisy.app cp /data/local/tmp/pokedaisy-stage-diagnostic.gba cache/compose-stage-probe/diagnostic.gba
```

```sh
adb shell am start -n com.pokedaisy.app/.ComposeStageProbeActivity --es layout native
adb shell am start -n com.pokedaisy.app/.ComposeStageProbeActivity --es layout compose
adb logcat -s pokedaisy/stage-probe pokedaisy/touch
```

Finish or force-stop the first mode before opening the other. The native core is process-wide.

```sh
adb shell am force-stop com.pokedaisy.app
```

On an emulator, rotate the running probe with `adb shell wm user-rotation lock 0` (portrait) and
`adb shell wm user-rotation lock 1` (landscape). Verify the screenshot dimensions or `dumpsys window displays`;
writing the rotation setting alone can leave the display unchanged. Restore rotation with
`adb shell wm user-rotation free` when finished.

The toolbar opens a companion window, resizes the stage without replacing the game view, prints a report and
deliberately stalls the UI thread for 200 ms. The stall is an input-routing diagnostic, not normal app work.
Reports include the game view identity, surface creation count, engine frames, rendered-frame counters and input mask.
Press logs include the input callback's thread. Native input-window event-delay logs remain the existing debug logs.

## Checks and interpretation

Check that the stripes remain visible with the companion window and controls drawn above them. Open and close the
window repeatedly, resize, rotate and background/reopen the probe. A layout resize should retain the renderer view;
a background lifecycle may recreate the surface. Verify that touch input reaches the core, returns to zero on
release, and is withheld while the companion window owns the screen. On supported Android builds, ordinary pad
presses should report the `pokedaisy-touch` thread. Samsung and failed native-window setup retain the existing
UI-thread fallback.

An emulator can establish functionality and reveal surface/input-lifetime faults. Its software graphics timing
does not establish physical-device latency or production frame pacing. Before replacing Android's production
containers, compare the current activity and candidate on real hardware under companion load, including
touch-to-visible-response, press dispatch, frame-time tails and the fallback input path. DS, skins, folds, display
swapping, full modal navigation and held-key suppression also remain migration acceptance checks.

## Recorded result

The Android 14 / API 34 ARM64 emulator (Pixel 5 profile, software graphics, muted and headless) passed these checks
for both hosts:

- The real native renderer displayed the generated diagnostic with the shared companion and touch controls.
- Portrait, narrower stage and verified landscape retained the same renderer view and one surface creation.
- Opening and closing the shared companion window preserved the renderer and its layer ordering.
- A-button presses used `pokedaisy-touch`, set the core input mask to 1 and returned it to 0 on release.
- During a deliberate 200 ms UI-thread stall, the input callback ran before the stall ended: 80 ms after its start
  in the native host and 92 ms in the Compose host. These are injection timestamps relative to the stall, not
  touch latency measurements.

`./gradlew :app:assembleDebug -Pquick` and `make test-quick` passed. These are functional interoperability results;
the production migration and hardware performance checks above remain open. The final build also exited cleanly
with a missing diagnostic and started, backgrounded and reopened the Compose probe without a crash.
